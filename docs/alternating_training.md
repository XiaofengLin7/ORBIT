# Alternating Actor / Summarizer Training

This document covers two training modes for experiments where action policy and summarization/reflection head are trained separately:

1. **Summarizer-only** — actor permanently frozen, only the summarizer trains.
2. **Alternating two-model** — actor and summarizer are separate models that take turns training every T steps.

---

## Architecture overview

Every trajectory produces two kinds of trainable tokens:

| Token type | Generated by | Mask |
|---|---|---|
| Action tokens | One of the two models | 1 = contributes gradient |
| Summary / reflection tokens | One of the two models | 1 = contributes gradient |

"Freezing" a model is implemented via **routing + masking**, not `requires_grad=False`:

- Routing action calls to the **frozen ref vLLM** (external process at port 8765) → those tokens never enter the PPO loss.
- Setting `response_mask=0` on summary/reflection positions in `assemble_segments` → those tokens are excluded from the loss even though they are still generated (context continuity is preserved).

### Summarizer phase

```
Action turns  → ref vLLM (frozen actor model, port 8765)   → mask=0, no gradient
Summary turns → training vLLM (summarizer model)            → mask=1, PPO gradient
```

### Actor phase

```
Action turns  → training vLLM (actor model)                 → mask=1, PPO gradient
Summary turns → ref vLLM (frozen summarizer model, port 8765) → mask=0, no gradient
```

Both modes use the same `SummarizingAgentExecutionEngine`. The `training_phase` attribute (set by the trainer before each rollout batch) controls which vLLM receives which call type.

### Code entry points

| Component | File | Role |
|---|---|---|
| Phase routing | `trainers/summarizing_engine.py` `_get_action_response`, `_get_summary_response` | Routes each call to the right engine based on `training_phase` |
| Summary mask zeroing | `trainers/summarizing_engine.py` `assemble_segments` | Zeros `response_mask` at `is_summarization=True` positions in actor phase |
| Phase tracking | `trainers/multi_episode_trainer.py` `init_envs_and_agents` | Checks step counter, fires `_do_phase_switch` when `phase_steps_done >= T` |
| Checkpoint swap | `trainers/multi_episode_trainer.py` `_do_phase_switch` | Save → restart ref vLLM → load → continue |

## Prerequisites

**Two GPUs required.** GPU 0 runs the verl FSDP training + training vLLM. GPU 1 runs the frozen ref vLLM.

Start the ref vLLM first in a **separate terminal** and keep it alive:

```bash
cd /projectnb/replearn/xfl/explorer
conda activate icx

CUDA_VISIBLE_DEVICES=1 vllm serve Qwen/Qwen3-8B \
    --served-model-name ref-model \
    --port 8765 \
    --gpu-memory-utilization 0.5 \
    --max-model-len 32768 \
    --dtype bfloat16
```

Verify:

```bash
curl -s http://localhost:8765/v1/models | \
    python3 -c "import json,sys; print(json.load(sys.stdin)['data'][0]['id'])"
# ref-model
```

## Mode 1 — Summarizer only

Only the summarizer/reflection head trains. The actor is frozen on the ref vLLM for the entire run. No phase switching, no checkpoint swaps, no `alternating.*` config needed.

```bash
REF_MODEL_URL=http://localhost:8765/v1 \
REF_MODEL_NAME=ref-model \
MODEL_PATH=Qwen/Qwen3-8B \
CARRYOVER=obs_action_reflection \
MODE=episodic \
EXP_NAME=qwen3-8b_summ_only \
bash scripts/train_maze.sh
```

`alternating.enable` defaults to `false` — the ref vLLM you started manually holds frozen actor weights for the whole experiment. You never need to restart it.

**What trains:** summary and reflection tokens (`response_mask=1`). Action tokens are routed to the ref vLLM and excluded from the PPO loss (`response_mask=0` implicitly, because those steps are never appended to `episode_steps`).

## Mode 2 — Alternating two-model training

Two separate models diverge from the same pretrained checkpoint and alternate every T steps. At each phase switch the trainer:

1. Saves the current model to its dedicated checkpoint directory.
2. Kills the existing ref vLLM and restarts it pointing to the saved checkpoint.
3. Loads the other model's latest checkpoint into the FSDP training slot.
4. Continues under the new phase.

```bash
REF_MODEL_URL=http://localhost:8765/v1 \
REF_MODEL_NAME=ref-model \
MODEL_PATH=Qwen/Qwen3-8B \
CARRYOVER=obs_action_reflection \
MODE=episodic \
EXP_NAME=qwen3-8b_two_model_T100 \
bash scripts/train_maze.sh \
    +rllm.agent.summarization.alternating.enable=true \
    +rllm.agent.summarization.alternating.T=100 \
    +rllm.agent.summarization.alternating.initial_phase=summarizer \
    "+rllm.agent.summarization.alternating.actor_ckpt_dir=checkpoints/two_model/actor" \
    "+rllm.agent.summarization.alternating.summarizer_ckpt_dir=checkpoints/two_model/summarizer" \
    "+rllm.agent.summarization.alternating.ref_vllm_cmd=CUDA_VISIBLE_DEVICES=1 vllm serve {ckpt} --served-model-name ref-model --port 8765 --gpu-memory-utilization 0.5 --max-model-len 32768 --dtype bfloat16" \
    +rllm.agent.summarization.alternating.ref_startup_timeout=300
```

Note that `CUDA_VISIBLE_DEVICES=1` is embedded inside `ref_vllm_cmd` — the trainer restarts the ref vLLM as a subprocess and must explicitly assign it to GPU 1. The ref vLLM you started manually in the prerequisites will be killed at the first phase switch.

### Alternating config reference

| Key | Default | Description |
|---|---|---|
| `alternating.enable` | `false` | Must be `true` to activate alternating. |
| `alternating.T` | `100` | Training steps per phase before switching. |
| `alternating.initial_phase` | `summarizer` | Which phase to start with: `summarizer` or `actor`. |
| `alternating.actor_ckpt_dir` | `checkpoints/alternating/actor` | Where actor checkpoint is saved/loaded at each switch. |
| `alternating.summarizer_ckpt_dir` | `checkpoints/alternating/summarizer` | Where summarizer checkpoint is saved/loaded. |
| `alternating.ref_vllm_cmd` | `vllm serve {ckpt} ...` | Full vLLM serve command. `{ckpt}` is substituted with the checkpoint path at switch time. |
| `alternating.ref_startup_timeout` | `300` | Seconds to wait for the restarted server before erroring. |

### What to watch in the logs

At startup:
```
[alternating] enabled: T=100, initial_phase=summarizer,
              actor_ckpt=checkpoints/two_model/actor,
              summ_ckpt=checkpoints/two_model/summarizer
```

At each phase switch:
```
[alternating] phase switch: summarizer → actor
[alternating] saving summarizer checkpoint → checkpoints/two_model/summarizer
[alternating] checkpoint saved in 14.2s
[alternating] starting ref vLLM: CUDA_VISIBLE_DEVICES=1 vllm serve ...
[alternating] ref vLLM ready
[alternating] no actor checkpoint yet at checkpoints/two_model/actor, continuing with current FSDP weights
[alternating] switch complete in 98.3s, now in actor phase
```

First switch into each phase produces the "no checkpoint yet" message — this is expected; both models share weights until their first respective training phase.

### wandb metrics

| Metric | Meaning |
|---|---|
| `training/phase` | `0.0` = summarizer phase, `1.0` = actor phase |
| `training/phase_steps_done` | Steps completed in the current phase (resets at each switch) |

## Tuning T

| T value | Effect |
|---|---|
| Small (10–20) | More frequent switches; models interact more but each gets fewer gradient steps per phase. |
| Medium (50–100) | Reasonable starting point. At maze scale (~90s/step), each phase is 1.5–2.5 hours. |
| Large (200+) | Each model trains deeply before being frozen; risks overfitting to the frozen counterpart. |

---

## Checkpoint storage

Each save writes approximately 16–20 GB (8B weights + per-rank optimizer shards). Ensure at least **50 GB free** in the checkpoint parent directory before running.

---

## Switching from summarizer-only to alternating mid-experiment

If you have a trained summarizer checkpoint and want to start joint training, copy it as both models' initial weights:

```bash
cp -r checkpoints/summ_only/global_step_500/actor checkpoints/two_model/summarizer
cp -r checkpoints/summ_only/global_step_500/actor checkpoints/two_model/actor
```

Then resume with `initial_phase=actor` so you immediately start training the actor while holding the trained summarizer frozen:

```bash
REF_MODEL_URL=http://localhost:8765/v1 \
REF_MODEL_NAME=ref-model \
MODEL_PATH=Qwen/Qwen3-8B \
CARRYOVER=obs_action_reflection \
MODE=episodic \
EXP_NAME=qwen3-8b_two_model_from_summ \
bash scripts/train_maze.sh \
    trainer.resume_from_path=checkpoints/two_model/summarizer \
    +rllm.agent.summarization.alternating.enable=true \
    +rllm.agent.summarization.alternating.T=100 \
    +rllm.agent.summarization.alternating.initial_phase=actor \
    "+rllm.agent.summarization.alternating.actor_ckpt_dir=checkpoints/two_model/actor" \
    "+rllm.agent.summarization.alternating.summarizer_ckpt_dir=checkpoints/two_model/summarizer" \
    "+rllm.agent.summarization.alternating.ref_vllm_cmd=CUDA_VISIBLE_DEVICES=1 vllm serve {ckpt} --served-model-name ref-model --port 8765 --gpu-memory-utilization 0.5 --max-model-len 32768 --dtype bfloat16" \
    +rllm.agent.summarization.alternating.ref_startup_timeout=300
```

## Caveats

- **The ref vLLM is restarted at each phase switch.** This takes 60–120s (model load + GPU warmup). At T=100 with ~90s/step, that is <2% overhead.
- **Summarizer-only mode uses the same ref vLLM you started manually.** It is never restarted — it holds the original pretrained weights for the entire run.
- **Alternating mode takes ownership of the ref vLLM at the first phase switch.** The manually started server is killed and replaced by the trainer's managed subprocess. After that, do not manually kill port 8765 while training is running.
- **Both models maintain independent optimizer states.** Each checkpoint includes both model weights and Adam momentum. When a model is loaded back into the FSDP slot, its optimizer history is fully restored.
